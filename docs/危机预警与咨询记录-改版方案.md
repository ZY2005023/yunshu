## 一、先厘清：这个功能到底解决什么问题

**一句话：它不负责"发现学生有心理问题"，它负责把「系统识别到风险」变成「真的有人去介入」。**

它不是诊断工具，是**分诊 + 派单 + 留痕**工具。价值在三件别的东西替代不了的事上：

1. **弥补"学生不会主动说"这个结构性缺口。**
   真正危险的学生，往往不会走进心理中心 —— 怕被贴标签、怕被通知家长、怕同学知道。
   但深夜一个人时，他可能对着一台不会评判他的机器说出来。
   这是学校心理工作里唯一能触达"沉默的那部分人"的通道。

2. **把模糊的担忧变成可执行的工单。**
   "最近感觉有个学生不太对" → 无法派单、无法跟进。
   "3 级危机、来源 AI 对话、原话是『我不想活了』、用户是 XX、15:33 触发" → 可以派单。

3. **留痕与复盘。**
   万一出了事，学校需要能证明"我们识别到了、我们做了什么、什么时候做的"。
   这不是形式主义，这是责任边界。

> ⚠️ 但必须同时明确它**做不到**什么：关键词规则必然误报；AI 不能诊断；
> 系统**不是急救通道**；它无法替代人的判断。把这一点写清楚，比堆功能更重要。

## 二、典型使用场景

**场景 A · 深夜倾诉（最主要）**
22:47，学生在 AI 对话里说"我不想活了，觉得没意义"。
规则层命中 3 级 → 生成工单 → 通知值班老师 → 第二天一早上报前已经有人在处理。

**场景 B · 日记里的绝望**
学生不在对话里说，但在情绪日记里写下"撑不下去了"。
日记提交时同步走规则层检测 + AI 情绪分析（`riskLevel` 达标再补记一条）。

**场景 C · 量表自伤项**
PHQ-9 第 9 题得分 > 0（**与总分高低无关**）→ 直接记 3 级事件。
这类最容易漏：总分可能是轻度，但第 9 题有分就是危险信号。

**场景 D · 连续低分趋势（当前完全没有）**
连续 5 天情绪评分 ≤ 3。单条都不构成危机，但组合起来是明确的恶化信号。
**现在系统看不到这个维度** —— 只做单条判定，没有纵向趋势。

**场景 E · 误报（占比很高，必须正视）**
真实库里：「推荐几本关于焦虑的书」被判成 1 级危机事件（见第四节）。
如果不处理误报，值班老师两周后就会不看这个列表 —— **那才是最坏的结果**。

## 三、能提前发现与规避什么风险

| 风险 | 系统能做什么 | 现状 |
|---|---|---|
| **主动求助缺口** | 不依赖学生主动开口，AI 对话/日记都能触发 | ✅ 已实现 |
| **时间盲区** | 24 小时值守，深夜/假期也能记录 | ✅ 已实现（前提是通知配了） |

## 四、为什么现在「鸡肋」—— 证据清单

### 整条链条只通了两环

```
识别 → 通知 → 了解情况 → 介入 → 留痕 → 跟进 → 复盘
 ✓      ✗        ✗         ✗      ✓      ✗      ✗
```

**问题不在"识别不准"，在于识别之后什么都没接上。** 值班老师拿到一条工单，
既不知道**这是谁**，也不知道**发生了什么**，更不知道**该做什么**。

### 逐条证据（均可复核）

| # | 问题 | 证据 |
|---|---|---|
| 1 | **列表里没有「用户」列** | `crisis.vue` 的表格只有 等级/来源/触发方式/命中内容/触发片段/状态/时间。看到一行"危险信号"，不知道对应谁 |
| 2 | **详情只显示 `用户ID: 52` 这种数字** | `crisis.vue` 详情弹窗第 97 行；而库里 `user.username` / `nickname` 都有，**取得到却不取** |
| 3 | **只能看到 120 字的片段** | `core/crisis.py::snippet()` 截断到 `SNIPPET_MAX=120` |
| 4 | **能一键跳原始对话，但前端没做** | 接口已返回 `sessionId` / `diaryId`（实测确认），页面完全没用这两个字段 |
| 5 | **看不到这个人的历史** | 过往工单、量表结果、日记趋势 —— 一个都没有。**无法判断是否复发** |
| 6 | **没有任何处置指引** | 处置弹窗只有「已处置/处理中/误报忽略」三个单选 + 一个备注框。新手根本不知道该怎么办 |
| 7 | **处置不可追加** | `handleNote` 是一次性文本，处置完就锁死，**记不了后续跟进** |
| 8 | **不显示是谁处置的** | `handlerId` 存在且已返回，详情页不展示。多人值班时会重复联系同一个学生 |
| 9 | **「按风险等级排序」是假的** | 页头这么写，实际 `order_by(created_at.desc())` —— **1 级误报和 3 级危机混在同一屏** |
| 10 | **等级实际只有 1~3，但 UI/通知里出现了 4 级** | `crisis.vue` 筛选只有 1/2/3；而 `notifier.py` 的 `_LEVEL_TEXT` 里有「4 级 · 紧急」（本轮引入的小瑕疵，建议一并删掉） |
| 11 | **误报率高，且没有降噪机制** | 真实库数据见下 |
| 12 | **未配 webhook 时等于没有主动触达** | 只在服务端写 WARNING 日志 |

### 真实数据里的误报证据

```
id  等级  来源    内容片段                          判定
8   1     CHAT   「推荐几本关于焦虑的书」            ← 一条正常的求书请求
6   1     CHAT   「我考试前总是特别焦虑，有什么办法缓解吗」 ← 正常求助
5   1     CHAT   「我考试前总是特别焦虑…」            ← 同上
12  3     CHAT   「我今天想自杀咋办呀」              ← 真·高危
14  3     CHAT   「我不想活了，觉得没意义」          ← 真·高危
```

命中词是 `ATTENTION_TERMS` 里的「焦虑」。**问题是：1 级和 3 级在同一列表里按时间混排**，
老师要在一堆"求书单"里找出"想自杀"。这是分诊设计的缺失，不是算法问题。

## 五、预警触发后，各方应当做什么

### 学生侧（现在已有什么）

学生会在对话页看到**固定的危机求助卡片**（`consultation.vue` 第 174~185 行）：

- 固定标题与副标题：明确表达"你不需要一个人扛着"
- 求助热线列表（12356 / 北京心理危机干预中心 / 120、110 / 校内心理中心）
- 免责声明：AI 不能替代诊疗，也不是紧急救援
- 一个「我知道了」按钮

内容来自固定常量（`crisis_service.HELPLINES`），**不依赖 AI 是否"愿意"提供** —— 这个设计是对的。

**缺失的部分**：
- 没有"我现在就想找人聊聊"这类**一键求助**入口
- 卡片被「我知道了」关掉后，**没有任何留痕**（学生是否看到过，无从得知）
- 没有告诉学生"接下来会发生什么"（例如：可能有人会联系你）

### 管理员侧（现在缺一个 SOP）

系统应该把流程固化成引导，而不是靠值班老师自己摸索。建议的 SOP：

| 时间 | 动作 |
|---|---|
| 0~5 分钟 | 打开工单 → **跳转原始对话/日记**看完整上下文 → 翻该用户历史工单判断是否复发 |
| 5~15 分钟 | 判断：**真风险** / **误报** |
| 真风险·3 级 | 立刻联系辅导员/班主任；尝试联系学生本人；必要时通知家长；有即时危险 → 120/110 |
| 真风险·2 级 | 24 小时内约谈；告知辅导员关注 |
| 真风险·1 级 | 记入关注名单，不单独约谈（避免惊动） |
| 误报 | 标记忽略 + **填写误报原因**（用于调关键词规则） |
| 后续 | **追加跟进记录**（3 天后复查 / 已约谈 / 已转介），直到关闭 |

**当前系统只支持第 2 步和第 6 步的一部分**（"已处置"三个字 + 一行备注）。

## 六、危机预警改版方案

**核心思路：从「事件列表」改成「处置工作台」。**
管理员要的不是"有哪些事件"，是"**我现在该做什么，谁、发生了什么、做过什么**"。

### 6.1 列表页：先做分诊，再做展示

| 改动 | 理由 |
|---|---|
| 加 **「用户」列**（昵称 + 用户名） | 现在不知道是谁 |
| **默认按 `等级 desc, 时间 desc` 排序** | 3 级必须在最上面；改掉名不副实的"按风险等级排序" |
| **待处理置顶**，已处置默认折叠 | 已完成的别占视线 |
| 增加 「**我的待办** / 全部」切换 | 多人值班时各看各的 |
| 1 级事件默认收进「关注」折叠区 | 降噪，让真警不被淹没 |
| 增加「**该用户历史工单数**」列 | 复发一眼可见 |

### 6.2 详情页 → 处置工作台（一屏看全决策依据）

这是整个改版最关键的一屏。建议三栏：

```
┌── 左：这个人是谁 ────────┬── 中：发生了什么 ──────────┬── 右：我该做什么 ──────┐
│ 昵称（用户名）             │ 风险等级 + 命中词            │ 处置 SOP 清单           │
│ 注册时间 / 最近活跃         │ 触发时间                     │   □ 已查看原始记录      │
│ ── 历史工单（时间倒序）──   │ ── 完整上下文 ──             │   □ 已联系辅导员        │
│   • 10-01 3级 已处置       │ 完整消息正文（不再是 120 字）  │   □ 已联系学生本人      │
│   • 09-28 1级 误报         │ [打开原始会话] [打开日记]     │   □ 已通知家长          │
│ ── 最近量表 ──             │                              │ ── 处置结果 ──          │
│   PHQ-9 自伤项 3 分 ⚠️     │                              │   ○真风险 ○误报         │
│ ── 近 7 天日记 ──          │                              │ ── 跟进记录（可追加）──  │
│   迷你趋势线 + 均分         │                              │   10-02 15:40 已电话…   │
└──────────────────────────┴──────────────────────────────┴────────────────────────┘
```

关键点：

1. **一键跳原始记录** —— `sessionId` / `diaryId` 已经在接口里了，**这是当前最高性价比的改动**
2. **用户画像** —— 让"是否复发"变成一眼可见
3. **处置 SOP 清单** —— 把上面第五节的流程变成可勾选的清单，新手也能照着做

### 6.3 处置流程结构化

- `handleNote` 拆成「**采取措施**（多选，便于统计）+ 说明（自由文本）」
- 支持**追加跟进记录**（时间线，不覆盖历史）
- 显示**处置人**（谁在处理）

### 6.4 降噪与闭环（这条最容易被忽视，但最重要）

| 措施 | 说明 |
|---|---|
| 1 级不推通知 | 只入列表；避免"求书单"半夜响铃 |
| 误报原因必填 | 「误报忽略」时记录原因，用于调 `ATTENTION_TERMS` |
| 同类合并窗口延长 | 现在同来源 5 分钟内去重（`DEDUP_MINUTES`），建议对话类延长到 30~60 分钟 |
| 每日汇总 | 1 级事件每天一条汇总，不逐条推 |

## 七、咨询记录改版方案

### 7.1 先修真 bug（3 处，纯前端）

| 问题 | 现状 | 修法 |
|---|---|---|
| `userNickname` 字段不存在 | 头像位置**空白**（实际字段是 `nickname`） | 改用 `nickname`，空则回退 `username` |
| `lastMessageTime` 字段不存在 | 「时间」列**空白**（实际字段是 `startedAt`） | 改用 `startedAt` |
| 副标题写「可按关键词检索」 | 页面上**根本没有搜索框** | 补搜索，或去掉这句 |
| 列头错乱 | 「会话ID」列里放的是头像；「情绪日志」列里放的是会话标题 | 改为「用户」「会话」 |

> 这四个加起来就是用户说的"**大混杂的信息，毫无作用**"——
> 两列是空的、列名对不上内容、承诺的搜索不存在。

### 7.2 再改版：按"要不要关心"排序，而不是按时间

管理端的咨询记录**不是用来闲聊回看的**，是**找需要关注的人**。所以：

| 改动 | 理由 |
|---|---|
| 加**搜索框**（用户 / 消息关键词） | 兑现副标题的承诺 |
| 列表增加**风险标记** | 该会话是否产生过危机事件、是否有 3 级命中 —— 一眼过滤 |
| 默认**风险优先排序**，可切"最新" | 管理员第一眼要看的是有风险的 |
| 增加**时长**（`durationMinutes` 已有，未展示） | 判断真实投入 |
| 增加**筛选**：仅看有风险的会话 | 把 30 条降到 3 条 |
| 详情内**标记风险消息** | 在对话流里把命中的那条高亮 |
| 详情内提供**跳转**：该用户的工单 / 日记 / 量表 | 形成闭环，不用来回找 |

### 7.3 关于 `lastEmotionAnalysis`

该字段**恒为 null**（Java 版从未写入，见 README 第六节）。
改版时**不要再为它设计 UI** —— 要么先补齐写入，要么保持不展示。

## 八、实施顺序与优先级

| 优先级 | 内容 | 说明 |
|---|---|---|
| **P0** | 咨询记录页 4 个 bug 修复（字段名 / 列头 / 搜索框） | 纯前端，改动小，立刻消除"毫无作用" |

| **P1** | 工单详情加**一键跳原始会话/日记** | 接口字段已就绪，最高性价比 |
| **P1** | 工单详情加**用户画像**（历史工单 + 最近量表 + 日记趋势） | 需新增 1 个聚合接口 |
| **P2** | 处置 SOP 清单 + 跟进时间线 + 显示处置人 | 需扩表（跟进记录）+ 改接口 |
| **P2** | 咨询记录风险标记与筛选 | 需后端在会话行补风险字段 |
| **P3** | 降噪（1 级不推、误报原因、合并窗口） | 影响面较大，需与心理中心一起定策略 |
| **P3** | 连续低分趋势预警（场景 D） | 新能力，需先确认阈值与隐私边界 |

**建议先做 P0 + P1**：全部是"把已有数据接上"，不改数据结构，能一次把工单从"看不懂"变成"能用"。

## 九、必须说清的边界与风险

1. **这是辅助分诊，不是诊断。** 系统给出的等级是"值得看一眼"，不是医学判断。
2. **误报是必然的，设计目标是"不淹没真警"，不是"零误报"。**
   所以降噪（第六节 6.4）不是可选项，是核心功能。
3. **隐私边界要写进用户可见的说明。** 学生必须知道"风险情形会生成记录供心理老师查看"
   —— 这一点已在 `PolicyDialog.vue` 中如实披露，改版时不要退回去。
4. **通知没配就等于没有。** 上线前必须配好 `CRISIS_WEBHOOK_URL`，并让值班的人知道消息发到哪个群。
5. **不要把"处置率"当 KPI。** 否则会诱导值班老师把所有工单点成"已处置"，
   留痕反而变成造假。要衡量的是**首次响应时长**。

## 十、实施记录（2026-10-02）

P0 / P1 / P2 已全部落地，P3（降噪、趋势预警）未做 —— 它需要和心理中心一起定策略，
不是能单方面拍板的事。

### 10.1 数据库（migration 0004，已在 `mental_health_py` 执行）

| 变更 | 说明 |
|---|---|
| `crisis_event.measures` | VARCHAR(200)，处置时勾选的结构化措施，逗号分隔编码 |
| `crisis_follow_up` 表 | 一条工单可有多条跟进；`event_id` 建索引 |

⚠️ 建表时**必须显式写 `COLLATE utf8mb4_unicode_ci`**：只写 charset 会拿到 MySQL 8 的表级
默认 `utf8mb4_0900_ai_ci`，与 0001 转过的表不一致，JOIN 时报 "Illegal mix of collations"。

### 10.2 新增/改造的接口

| 接口 | 说明 |
|---|---|
| `GET /api/admin/crisis/page` | 行里补 `username` / `nickname` / `handlerName` / `measures` / `followUpCount`；新增 `keyword`（按账号昵称过滤） |
| `GET /api/admin/crisis/{id}/context` | **新增**。一屏返回：用户画像 + 历史工单 + 量表 + 日记趋势 + 触发原文（完整不截断）+ 跟进记录 + 处置清单 + 措施选项 |
| `GET /api/admin/crisis/{id}/follow-ups` | **新增** |

### 10.5 一个实现上的坑（值得记下来）

`CrisisContextOut.diary_trend` 最初写成 `dict[str, Any]`，结果 JSON 里出现的是
`low_days` 而前端按 `lowDays` 读 —— 因为 **`alias_generator` 只作用于模型字段，
dict 的键不会被转成 camelCase**。这类"字段名不同步"正是本项目最常见的静默失效形态，
所以把它改成了强类型的 `CrisisDiaryTrend`。
