## 一、通用约定

### 1.1 统一响应包装 Result

**所有非 SSE 接口**的响应体都被包装成这个结构：

```json
{
  "code": "200",
  "msg": "操作成功",
  "data": { }
}
```

**注意：`code` 是字符串，不是数字。** 这是最容易踩的一处 —— 前端判定大概率写的是 `res.code === '200'`，Python 版若返回整数 `200` 或 `res.code == 200`，全站接口判定失效。

字段名是 `code` / `msg` / `data`（**不是 `message`**）。

`Result.ok()` 无参时 → `data` 为 `null`。

### 1.2 错误码对照表

| code | 含义 | 备注 |
|---|---|---|
| `200` | 操作成功 | msg = "操作成功" |
| `-1` | 操作失败 | msg = "操作失败"（`ResultCode.ERROR`，**代码中未被实际使用**） |
| `401` | 暂未登录或 token 已过期 | 认证入口点返回 |
| `500` | 系统错误 | 兜底异常 |
| `400` | 参数错误 | 校验失败时 `data` 字段承载具体提示，多个提示用 `", "` 连接 |
| `4001` / `4002` | 缺少必要参数 / 参数格式不正确 | 已定义，代码中未见使用 |
| `5001` ~ `5008` | 文件类错误（不存在/上传失败/超限/类型不支持等） | |
| `6000` / `6001` / `6002` | 业务失败 / 用户名已存在 / 用户不存在 | |

> ⚠️ **关于 `-1`**：`ResultCode.ERROR` 虽然定义为 `-1`，但代码里没有地方真正抛它。
> **业务异常 `new BusinessException("提示")` 走的是 `6000`**（单参构造器内部用
> `ResultCode.BUSINESS_ERROR.getCode()`，见 `BusinessException` 第 19 行）。
> 前端如果按 `-1` 判定业务错误，会全部漏掉 —— 移植时按 **6000** 实现。
> Python 侧已由 `test_password_mismatch` 用例锁死。
| `A0230` | token 无效、**已过期**、**已加入黑名单** | ⚠️ 三者共用同一个 code |
| `A0231` | token 已被禁止访问 | 账号状态异常时用于刷新拦截 |
| `A0300` | 访问权限异常 | `@PreAuthorize` 拒绝时返回 |
| `A0301` | 访问未授权 | 未登录访问受保护资源时返回 |

> ⚠️ **迁移陷阱**：`TOKEN_INVALID` / `TOKEN_EXPIRED` / `TOKEN_BLOCKED` 三个枚举的 code 都是 `A0230`，
> 看起来像笔误，但前端很可能依赖这一个值做统一跳转登录。
> **Python 版不要"顺手修正"成三个不同的码**，必须保持原样，或先确认前端逻辑。

### 1.3 认证方式与请求头

```
Authorization: Bearer <access token>
```

- 请求头名称可配，默认 `Authorization`，前缀 `Bearer `（**注意前缀后面带一个空格**）
- **兼容逻辑**：若 `Authorization` 头为空，会回退读取名为 `token` 的头（兼容旧客户端）
- 令牌形式：JWT（无状态，服务端不存 session）

### 1.4 JWT 结构（迁移必须逐字对齐）

| 项 | 值 |
|---|---|
| 算法 | **HMAC256** |
| 签发者 `iss` | `mental-health-assistant` |
| secret 位置 | 环境变量 `JWT_SECRET`，**最小长度 32**，不足直接抛异常 |
| access token 有效期 | 默认 **1800000 ms（30 分钟）** |
| refresh token 有效期 | 默认 **604800000 ms（7 天）** |

自定义 claims：

| claim | 类型 | 说明 |
|---|---|---|
| `userId` | Long | 用户主键 |
| `username` | String | 用户名 |
| `roleType` | Integer | 1 = 普通用户，2 = 管理员 |
| `typ` | String | `"access"` 或 `"refresh"`，用于区分两种令牌 |
| `exp` / `iat` | int | **秒级** Unix 时间戳 ⚠️ 不是毫秒 |

> ⚠️ **单位陷阱**：`application.yml` 里配的 `jwt.expiration` 是**毫秒**（1800000），
> 但 `java-jwt` 的 `withExpiresAt(Date)` 落进 payload 时是**秒**（JWT 标准 NumericDate）。
> 中间有 `/1000` 转换，别在 Python 侧直接拿毫秒当 exp 用。
> 已由 `mental-health-py/apps/api/tests/test_contract_core.py` 的
> `test_exp_is_seconds_not_milliseconds` 用例锁死。

标准字段包括 `iss`、`iat`、`exp`。

**关键业务规则**（`JwtTokenUtil.validateToken`）：

1. `typ == "refresh"` 的令牌**不能直接访问业务接口**（返回 null → 401）
2. 刷新接口只接受 `typ == "refresh"`，防止用 access token 无限续期
3. `userId` / `username` / `roleType` 三者任一缺失 → 校验失败
4. refresh token 有黑名单，且比对**签发时间 vs 用户全量吊销时间点**

> **迁移要点**：只要 Python 侧保持同一把 secret + 上述 claim 结构，PyJWT 与 java-jwt 可以互相验签，
> 老 token 能平滑过渡。改任何一个字段都会导致全体登录态失效。

### 1.5 权限模型

两层防护：

**第一层 · URL 白名单**（`SecurityConfig.PUBLIC_PATHS`，共 10 条，匿名可访问）：

```
/                        根路径
/api/user/login          登录
/api/user/add            注册
/api/user/refresh        刷新令牌
/files/**                上传的静态文件（img 标签直引，浏览器不带 Authorization 头）
/actuator/health         健康检查（匿名只见 UP/DOWN，不含组件明细）
/actuator/health/**
/v3/api-docs/**          接口文档，默认关闭
/swagger-ui/**
/swagger-ui.html
/error
```

除白名单外，**其余一切路径都必须携带有效 token**。

> **隐性耦合提醒**：`PUBLIC_PATHS` 这个数组同时被 `JwtAuthticationFilter` 通过静态方法
> `SecurityConfig.isPublicPATH()` 复用。迁移时只改一处会漏 —— 两边要同步。

**第二层 · 方法级注解** `@PreAuthorize("hasRole('ADMIN')")`，等价于 **`roleType == 2`**：

- 类级标注（整个 Controller 都需 ADMIN）：`CrisisEventController`、`DataAnalyticsController`
- 方法级标注：`EmotionDiaryController` 的 `/admin/page` 与 `/admin/{id}`；`KnowledgeArticleController` 的 4 个写操作；`PsychologicalChatController` 的 `/admin/sessions`

> **迁移陷阱**：Spring Security 的 `hasRole` 会自动给角色加 `ROLE_` 前缀。
> 但本项目 JWT 里根本没有 `ROLE_` 前缀、也没有 `authorities` 声明，实际是靠 `roleType == 2` 判定的
> （具体见 `JwtAuthticationFilter`）。Python 侧请直接判 `roleType == 2`，不要照搬 Spring 的角色前缀机制。

### 1.6 分页约定

- 通用分页参数：`currentPage`（默认 1）、`size`（默认 10）
- `size` 上限：**100**（由 `PageQueryDTO.getSize()` 截断，以及 MyBatis-Plus 分页插件 `maxLimit=100`）
- ⚠️ **例外**：危机事件接口 `/api/admin/crisis/page` 内部写死上限 **50**，与全局 100 不一致

### 2.1 用户模块 `/api/user`（6 个）

**1. `POST /api/user/login`** 🔓 登录
- 请求体：

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| username | string | 是 | ≤100（可传用户名或邮箱） |
| password | string | 是 | 6~50 |

- 返回 `data`：

```json
{
  "token": "string",
  "refreshToken": "string",
  "roleType": "1",
  "userInfo": { }
}
```

> `roleType` 是**字符串**（`userInfo.userType.toString()`），不是数字。

**2. `POST /api/user/add`** 🔓 注册
- 请求体：

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| username | string | 是 | 3~50，正则 `^[a-zA-Z0-9_]+$` |
| email | string | 是 | 邮箱格式，≤100 |
| nickname | string | 否 | ≤50 |
| phone | string | 否 | 正则 `^$|1[3-9]\d{9}` |
| password | string | 是 | 6~50 |
| confirmPassword | string | 是 | 需与 password 相等 |
| gender | integer | 否 | 1=男 2=女 |
| userType | integer | 否 | **默认 1**，但服务端未强制 ⚠️ 见第六章 |
| birthday | date | 否 | ISO 日期 |

- 返回 `data`：与下面 `/api/user/current` 相同的用户详情对象
- 业务校验：用户名重复 → `6001`；邮箱重复 → `6001`；两次密码不一致 → 业务异常

**3. `POST /api/user/refresh`** 🔓 用 refresh token 换新的 access token
- 请求体：`{ "refreshToken": "string" }`（必填）
- 返回 `data`：同登录
- 完整校验链（**缺一不可**）：
  1. refresh token 签名与有效期校验，失败 → `A0230` "刷新令牌无效或已过期，请重新登录"
  2. `typ` 必须等于 `"refresh"`，否则 → `A0230` "令牌类型不正确"
  3. 令牌不在黑名单，否则 → `A0230` "登录状态已失效，请重新登录"
  4. `userId` 必须存在
  5. 用户存在且 `status == 1`，否则 → `A0231` "账号状态异常，请重新登录"
  6. 令牌签发时间必须晚于该用户的全量吊销时间点，否则 → `A0230`

**4. `GET /api/user/current`** 🔑 获取当前登录用户
- 返回 `data`（用户详情对象，字段名必须一致）：

```json
{
  "id": 1,
  "username": "string",
  "email": "string",
  "nickname": "string",
  "avatar": "string",
  "phone": "string",
  "gender": 1,
  "genderDisplayName": "男",
  "birthday": "2000-01-01",
  "userType": 1,
  "userTypeDisplayName": "普通用户",
  "status": 1,
  "statusDisplayName": "正常",
  "displayName": "string",
  "createdAt": "...",
  "updatedAt": "..."
}
```

派生字段的生成规则（**必须照搬**）：

| 字段 | 规则 |
|---|---|
| `genderDisplayName` | null → "未知"；1 → "男"；2 → "女"；其他 → "未知" |
| `userTypeDisplayName` | 1 → "普通用户"；2 → "管理员"；其他 → "未知" |
| `statusDisplayName` | 0 → "禁用"；1 → "正常"；其他 → "未知" |
| `displayName` | nickname 非空则取 nickname，否则取 username（注意 `trim()` 后判空） |

**5. `POST /api/user/logout`** 🔑 退出登录
- 请求体**可选**：`{ "refreshToken": "string" }`
- 行为：把当前请求携带的 access token 拉黑；若 body 带了 refreshToken，把它也拉黑
- 返回 `data`：null

**6. `POST /api/user/password`** 🔑 修改密码
- 请求体：

| 字段 | 类型 | 约束 |
|---|---|---|
| oldPassword | string | 必填 |
| newPassword | string | 必填，6~64 |
| confirmPassword | string | 必填 |

- 两次新密码不一致 → 业务异常 "两次输入的新密码不一致"
- 成功后该用户**此前签发的所有令牌立即失效**（全量吊销机制）

### 2.5 文件上传 `/api/file`（1 个）

**19. `POST /api/file/upload`** 🔑 上传
- **multipart/form-data** 表单，不是 JSON
- 表单字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| file | 是 | 文件本身 |
| businessType | 否 | 业务类型，决定存储子目录 |
| businessId | 否 | 业务对象 ID |
| businessField | 否 | 业务字段名 |

  - 扩展名白名单：`jpg,jpeg,png,gif,webp,bmp,pdf,txt,doc,docx,xls,xlsx,mp4,mp3,wav`
  - **校验文件头魔数**比对扩展名，防止改后缀伪装
  - `businessType` 经过路径穿越防护（规范化后必须仍在上传根目录下）
  - 存储文件名改为 UUID，防止枚举
- 返回 `data`：

```json
{
  "fileId": 1,
  "filePath": "/files/{businessType}/{uuid}.{ext}",
  "url": "/files/{businessType}/{uuid}.{ext}",
  "originalName": "原名.jpg",
  "fileType": "IMG",
  "fileSize": 102400
}
```

> `filePath` 与 `url` 目前是同一个值。

### 2.6 心理咨询 `/api/psychological-chat`（7 个）

- 请求体：`{ "sessionTitle": "≤200", "initialMessage": "必填, ≤2000" }`
- 副作用：落库会话 + 首条用户消息，**并对首条消息执行一次危机检测**
- 返回 `data`：

```json
{
  "sessionId": "session_123",
  "userHash": 1,
  "initialMessage": "string",
  "startTime": 1700000000000,
  "expiryTime": 1700086400000,

```

> `sessionId` 格式为 `"session_" + 数据库主键`；`startTime` / `expiryTime` 是**毫秒时间戳**；会话有效期 **24 小时**。

**21. `POST /api/psychological-chat/stream`** 🔑 SSE 流式对话
- 见第三章，这是整个迁移最难的一处

**22. `GET /api/psychological-chat/sessions`** 🔑 我的会话列表
- 查询参数：`currentPage`（默认 1）、`size`（默认 10）
- 返回 `data`：`{ "records": [...], "total": 0 }`，records 每项：

| 字段 | 说明 |
|---|---|
| id / userId / sessionTitle / startedAt / lastEmotionAnalysis | 会话字段 |

## 三、SSE 流式协议（难点）

接口：**`POST /api/psychological-chat/stream`**，响应头 `Content-Type: text/event-stream`

请求体：`{ "sessionId": "必填", "userMessage": "必填, ≤2000" }`

### 事件序列

```
event:crisis   ← 仅当检测到危机时，在 AI 回复之前下发
event:message  ← 0..N 条，逐段吐出 AI 回复
event:done     ← 恒定最后一条（成功路径）
event:error    ← 失败路径，替代后续内容
```

**每个事件之间强制延迟 50ms**（`delayElements(Duration.ofMillis(50))`）。
缺失这一步不会报错，但前端会被大量碎片冲垮，表现为 UI 卡死或渲染错乱。

### 每种事件的 data

| 事件 | data 内容 |
|---|---|
| `crisis` | `Result.ok({ level, title, subtitle, helplines, disclaimer })` |
| `message` | `Result.ok({ content, type: "normal" })` |
| `done` | **`"{}"`** ← 裸 JSON，**未被 Result 包装** |
| `error` | `Result.error("500", "<可读提示>", null)` |

> ⚠️ **最容易复制错的一处**：`done` 事件的 data 是字面量 `{}`，
> 不是 `{code:"200", msg:"操作成功", data:null}`。前端判定很可能直接看data是否为空对象。

具体报文形态：

```
event: crisis
data: {"code":"200","msg":"操作成功","data":{"level":3,"title":"...","subtitle":"...","helplines":[],"disclaimer":"..."}}

event: message
data: {"code":"200","msg":"操作成功","data":{"content":"你好","type":"normal"}}

event: done
data: {}
```

### 错误分支

| 触发条件 | 行为 |
|---|---|
| sessionId 解析不出主键 | 立刻下发一条 `error`："会话ID格式错误，请新建会话后重试" |
| 归属校验失败（不是本人也不是管理员） | 立刻下发一条 `error`，内容为业务异常消息 |
| AI 调用失败（网络/超时/额度） | 在已吐出的 message 之后追加一条 `error`："AI 服务暂时不可用，请稍后再试"，**不让连接裸崩** |

### 服务端副作用（异步发生）

- AI 回复完成后**完整内容落库**，超过 **20000 字符会被截断**再存
- 多轮记忆以 `conversation_{sessionId}` 为 key 保存
- 使用的模型名（`deepseek-chat`）会写入消息的 `ai_model` 字段

### Python 实现要点

FastAPI 里用 `StreamingResponse(async_generator, media_type="text/event-stream")`，
把 Reactor 的 `doOnNext` / `doOnComplete` / `doOnError` 分别落到 generator 的
操作、结束前、`except` 分支里。**注意：generator 被提前取消时（客户端断开），
要确保已吐出的内容仍然落库，避免白烧 token 丢数据。**

## 五、迁移时必须原样保留的坑

1. **`Result.code` 是字符串** —— 返回整数会让全站判定失效
2. **`A0230` 被三个 token 错误共用** —— 不要"修正"成三个不同的码
3. **`done` 事件的 data 是裸 `{}`** —— 不是 Result 包装
4. **SSE 的 50ms 延时** —— 缺了不会报错，但前端体验崩坏
5. **危机检测的分级阈值与关键词表** —— 错判的后果是安全问题（见 `CrisisDetectionService`，需单独文档化）

7. **`/session/{id}/emotion` 是单数、`/sessions/{id}/messages` 是复数** —— 路径不一致，别修正
8. **文章详情访问即 +1 阅读数** —— 这是个副作用，漏了会影响数据
9. **`roleType` 在登录响应里是字符串，在 JWT claim 里是整数** —— 两处类型不同
10. **`statusText` 的映射值**：文章是 "已发布"/"草稿"，分类是 "启用"/"禁用"

## 六、发现的安全问题

> 本次静态分析顺手发现，**与迁移无关但应当处理**。

**注册接口可以任意提权成为管理员**

- 位置：`POST /api/user/add`（**匿名白名单接口**）+ `UserService.register`
- 现象：请求体里的 `userType` 由客户端传入，服务端只校验它是否为合法值（1 或 2），
  **没有把它强制置为普通用户**，随后该值直接写库。
- 后果：任何人传 `"userType": 2` 即可注册出管理员账号，进而访问全部 👑 接口。
- 现状：原版代码存在此问题。
- 建议：Python 版在注册时**强制 `userType = 1`**；如需开放管理员注册，改为管理员邀请制并提供受保护的管理员接口。
